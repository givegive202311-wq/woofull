# AIっぽさを無くすSEO記事作成ワークフロー

個人開発者Maks氏(@maks6361)が公開していたワークフローを、Woofullのコードベース向けに落とし込んだルール。
Googleが見ているのは「AIが書いたか人間が書いたか」ではなく「役に立つか／オリジナルか／人のために書かれたか」。
このドキュメントに従わずに`/guides`配下へ記事を追加しない。

キーワードの優先順位（ロングテール優先の考え方）は `docs/seo/strategy.md` を参照。画像・文字数などの品質基準もそちらに定義している。

## ①キーワードを勝手に選ばせない

- 記事テーマは必ず `docs/seo/keyword-list.md` の一覧から選ぶ。AIが「近いテーマだから」と自己判断で新しいテーマを作らない。
- 一覧に候補が無い状態で記事を書き進めない。**先に一覧へキーワード（検索意図つき）を追加してから**書き始める。
- 一覧のステータスが `queued`(執筆待ち) のものだけを書く。`draft`(検討中・未承認) のキーワードでは書かない。

## ①.5 競合の1位記事を必ず調べる（構成を作る前に）

キーワードをTier1として確定させる前に、**そのキーワードで現在1位の記事を必ず1つ確認する**。見るポイントは以下。

- 運営元の規模（大手企業のオウンドメディアか、個人ブログか）
- 監修者・著者情報の有無（E-E-A-T。特に犬の健康・しつけ系はここが強いと勝ちにくい）
- 見出し（H2/H3）の数、目次の有無
- 文字数の目安
- 画像・図解の枚数
- 内部リンクの数、FAQの有無、構造化データっぽい要素の有無
- 公開日・更新日

### 判定と対応（両輪戦略）

| 競合の強さ | 対応 |
|---|---|
| 個人ブログ・情報が薄い・監修者なし | そのままTier1として執筆してよい |
| 大手メディア・監修者あり・構成が厚い（今回のCainz事例など） | **1本にまとめようとせず、両方やる**：①元のキーワードの記事は`queued`のまま残し、長期投資として後から画像・見出し・文字数を競合水準まで厚くする　②同時に、競合が拾いきれていない具体シチュエーション（対象・状況・悩みをさらに一段具体化したもの）を新しいTier1キーワードとして`keyword-map.md`に追加し、別記事として先に執筆する。どちらか一方だけをやらない |

うちが構造的に勝ちやすい要素（大手が手薄なことが多い）：
- `directAnswer`による結論ファースト（AI検索エンジンの引用に強い）
- `faq`のFAQPage構造化データ（大手でも入れていないことが多い）
- ニッチな状況（多頭飼い・賃貸・特定犬種など）への言及

大手に構造的に勝てない要素（短期間では埋まらない）：
- ドメインパワー・被リンク数
- 監修者・著者の専門性（E-E-A-T）

これらを理由に「勝てないから諦める」のではなく、「今すぐ勝てる部分（ロングテール派生）」と「時間をかけて育てる部分（元記事の強化）」を両方同時に進める。

## ②検索意図を先に決める

書き始める前に、読者が何を求めているかを1つに分類してから構成を作る。

| 意図 | 説明 | Woofullでの例 |
|---|---|---|
| 定義 | 「〜とは」を知りたい | 犬の分離不安とは |
| 手順 | やり方を知りたい | 早食い防止のやり方 |
| 比較 | 選択肢を比べたい | ベッドのタイプ比較 |
| 購入ガイド | 何を選べばいいか知りたい | マナーポーチの選び方 |
| トラブル対応 | 困りごとを解決したい | 歯磨きを嫌がる |
| リスト | まとめて知りたい | 留守番グッズまとめ |

キーワードをタイトルや本文に何度も詰め込むのではなく、この意図に答えることを優先する。

## ③商品情報は商品定義ファイルで検証する

- 商品について書く内容は、必ず `docs/seo/product-facts.md`（Supabaseの実データから生成）と照合する。
- このファイルには「ある機能」だけでなく「（要確認）＝断定できない情報」も明記している。**「要確認」マークが付いている項目は記事内で事実として断定しない**（例：「反射材付き」と書かない。「反射・蓄光仕様とされています」程度に留めるか、書かない）。
- 存在しないサイズ・カラー・素材・付属品を作らない。specsに無い数値を書かない。
- 在庫状態（stock_status）が `out_of_stock` の商品を「今すぐ買える」ように書かない。

## ④記事構成を固定する

`src/lib/articles.ts` の `Article` 型に対応する、以下の構成で統一する。

1. `title` — 検索意図が伝わるタイトル
2. `directAnswer` — 冒頭2〜3文で結論を先に言う（AI検索エンジン・強調スニペット向け）
3. `heroImage` — 記事冒頭に置く商品画像（実在するSupabase画像URLのみ。alt必須）
4. `body` — 見出し4〜6個程度の本文（Markdown）。本文中にも商品画像を最低1枚追加で挿入する（`heroImage`と合わせて記事全体で最低2枚）
5. `faq` — よくある質問4〜6個（FAQPage構造化データにも使う。ロングテールの疑問形をそのまま質問文にする）
6. 関連商品（`relatedProductSlugs` で明示指定。concept_tagまかせにしない）
7. CTA（`/products`または`/products/[slug]`への導線。既存テンプレートで自動表示）

画像・文字数の詳しい基準は`strategy.md`の「4. コンテンツの品質基準」を参照。

**画像の作り方**：優先順位は次の通り。
1. 商品がある記事は、実在するSupabase商品画像を使う
2. 手順・比較・ステップものの記事は、**SVGで図解を自作する**（完全無料）。`public/images/diagrams/`配下に`<slug>.svg`として保存し、ブランドカラー（オレンジ#F6A54B・ダーク#2D2D2D・クリーム#FFF8F1、丸ゴシック「Arial Rounded MT Bold」）で統一する。手順は`docs/seo/diagram-howto.md`を参照
3. 商品も図解も難しい記事は、無料写真素材（Unsplash/Pexels）か`public/images`の既存素材を使う
4. 画像生成MCPが接続されている場合はそれも使ってよい

存在しない画像URLを創作しない。

内部リンクは「関連する商品」ブロックと、本文中の他記事への言及で確保する。

## ⑤公開前に2回、AIっぽさを削る

**1回目：内容面**
- 誇張語（「革新的」「圧倒的」「劇的に」など）を削る
- 「〜しませんか？」を毎回使うなど、企業広告っぽい問いかけを削る
- 根拠のない断定（「みんな悩んでいる」「95%の飼い主が」等、出典のない数字）を削る
- 空のマーケ文句（「もっと快適な毎日を」だけで終わる文）を削る

**2回目：文体面**
- 同じ接続詞・同じ文末（「〜です。」の連続、「まず」「そして」の多用）を削る
- 長すぎる段落（5文以上）を分割する
- 記事ごとに同じ定型文を使い回さない（例：商品ページの「Woofullは〜を世界中から厳選しています」を毎記事末尾にコピペしない）
- ダッシュ（——）や過剰な箇条書きの多用を見直す

## ⑥スコアが低ければ構成に戻す

公開前に自己チェックする。基準に届かなければ**③④に戻ってやり直す**。

- [ ] 商品定義ファイルと矛盾する記述が無い（最重要）
- [ ] 人間が読んで自然か（テンプレ感がないか）
- [ ] 検索意図に対して結論が明確に書かれているか
- [ ] 在庫切れ商品を「買える」前提で書いていないか
- [ ] 他の記事とタイトル・想定キーワードが重複していないか（カニバリ防止）

## ⑦承認後だけ公開する

- `src/lib/articles.ts` への追加は「下書きとして提示→ユーザー確認」を経てから行う。無承認でまとめて大量公開しない。
- 公開後は `docs/seo/keyword-list.md` の該当行のステータスを `published` に更新する。

## 運用ファイルの役割

| ファイル | 役割 |
|---|---|
| `docs/seo/workflow.md` | このルール自体 |
| `docs/seo/keyword-list.md` | SEO戦略・コンテンツ管理表（キーワード一覧＋検索意図＋ステータス） |
| `docs/seo/product-facts.md` | 商品定義ファイル（ある機能／ない機能・要確認事項） |
